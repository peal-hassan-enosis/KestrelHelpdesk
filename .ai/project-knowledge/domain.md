# Domain and Authorization

## Ticket

`Ticket` has:

- `Id`
- `Title` (required, 5–100 characters)
- `Description` (required)
- `Priority` (`Low`, `Medium`, `High`, `Critical`)
- `Category` (`Hardware`, `Software`, `Network`, `Access`)
- `Status` (`Open`, `InProgress`, `Resolved`)
- `CreatedBy` Identity user ID
- nullable `AssignedToUserId`
- `CreatedAt` UTC timestamp
- `Comments`
- `Attachments`

Evidence: `KestrelHelpdesk.Core/Models/Ticket.cs`.

## Comment

`Comment` belongs to a ticket and contains text, author and creation time. `TicketCommentService` overwrites the ticket ID, author and timestamp using the authenticated user/server time before persistence.

## Roles

`AppRoles` defines exactly three application roles:

- Employee
- Agent
- Manager

`IdentitySeeder` creates those roles and development users at startup.

## Ticket lifecycle rules

`TicketService.CreateTicketAsync`:

- requires authentication;
- validates the ticket;
- sets `CreatedBy` from the authenticated user;
- always sets status to `Open`;
- clears assignment;
- sets `CreatedAt` to UTC now.

Therefore a client cannot select an arbitrary creator, initial status or initial assignee through the service.

`UpdateTicketAsync`:

- reloads the existing ticket;
- checks `TicketAccessPolicy.CanEdit`;
- preserves creator, assignment and original creation time;
- prevents a Manager from changing status through the update service;
- validates before persistence;
- publishes a ticket-change event when an Agent changes status.

## Ticket visibility/editing

`TicketAccessPolicy.CanView` allows:

- Manager: all tickets;
- ticket creator: their own ticket;
- Agent: tickets assigned to that Agent.

`CanEdit` currently uses the same rule.

`TicketQueryService` additionally enforces role-specific scopes:

- Manager requests become `ManagerAll`.
- Employee requests become `EmployeeOwn`.
- Agent requests use `AgentCreated` or `AgentAssigned` depending on the requested scope.

## Assignment rules

`TicketAssignmentService` allows only Agents and Managers to change assignment.

- Agent: only tickets they created, and only to themselves or unassigned.
- Manager: can assign/unassign and selected assignees must be valid Agents.
- Employee: cannot change assignment.

## Comments

A signed-in user can comment only when `TicketAccessPolicy.CanView` permits access to the ticket.

## Attachments

The README and `TicketForm.razor` establish a maximum of three attachments per ticket and a maximum individual file size of 10 MB. Supported extensions and image-processing rules are implemented by attachment services. Stored files are non-public and download is an authenticated HTTP endpoint that re-checks ticket access.

## Dashboard

Dashboard status counts are generated by `TicketQueryService.GetTicketStatusCountsAsync`, using the effective role/scope for the current user. Employees see their own created tickets; Agents can switch assigned/created scope; Managers receive the manager-all scope.

## Role management

The application provides a Manager-only role-assignment workflow for assigning Employee or Agent roles to registered users. A pending-role flow exists for authenticated users without an application role.

## Enforcement distinction

- UI restrictions: `[Authorize]`, `AuthorizeView`, disabled controls and conditional rendering.
- Service enforcement: Core service checks and `TicketAccessPolicy`.
- Database enforcement: EF relationships/constraints such as required attachment metadata and attachment-to-ticket foreign key.

Do not assume UI hiding alone is a security boundary.
